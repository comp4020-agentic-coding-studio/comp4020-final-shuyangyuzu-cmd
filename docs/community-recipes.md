# Community recipes

Implemented by Codex, 2026-11-07. This feature extends The Mixology Book inside the existing counter book; it does not change Meals/Drinks ordering, stamina, eating or game rules. Claude's menu expansion (`dd8e33c`) is included unchanged apart from the menu book's new embedded-view teardown hook.

**Superseded in part, 2026-11-08 (Claude): The Mixology Book is now The Recipe Book, shared by drinks and food.** Every recipe carries a `kind: 'drink' | 'food'`, chosen once at publish time. Discover's filters, the editor's fields (alcohol-free vs. optional prep/cook time), and the "Number of glasses"/"Servings" label all adapt to the chosen kind. Every house recipe and every recipe/plan snapshot saved before this round defaults to `'drink'` — see CLAUDE.md's matching 2026-11-08 entry for the exact compatibility mechanism and a real pointer-capture bug this round found and fixed in the new detail page's photo zoom. "Using the book" below is updated in place to describe the current shape; it is not a second, independent description.

## Using the book

- **Discover** includes house and community recipes, drinks and food alike. Search matches names, ingredients, tags and creator names, including partial words and one-character typos for words of at least four characters. Filters select source, recipe kind (All/Drinks/Food), alcohol-free drinks (drink-only — disabled when Food is chosen), and pantry readiness. Public results refresh approximately once a second while this view is open.
- **View recipe** opens a two-page book spread (2026-11-08): a left page with the photo, name, description, author, equipment and kind-specific info (alcohol content for a drink; prep/cook time for food), and a right page with the servings control, ingredients, steps, garnish, source and the Save recipe / Add to party plan / Report actions. The left page's photo supports a temporary, reading-only zoom (buttons, scroll wheel, pinch) that never changes the author's saved photo crop. A back link returns to wherever the page was opened from (Discover or Party Plan's Saved tab), restoring that screen's exact search/filter state and scroll position.
- **My Recipes** holds private drafts and published posts. Choose Drink or Food, fill the template, upload an optional photo, adjust the photo width/crop, enter ingredient measures and preparation steps, and preview (in the same two-page layout as a real View recipe) before publishing. Drag the outer bottom edge to set header height (180-440 px); the photo fills that height. Drag the right photo edge to set its width (20-60%). Both handles support keyboard arrows. Add/change/remove controls live inside the photo area; the separate upload row and crop/zoom sliders were removed following user feedback. Old crop values remain compatible; replacing a photo centres it. On mobile, ingredients and preparation stack vertically.
- Draft edits autosave after 900 ms. Publishing is explicit: editing a published recipe does not change its public version until Publish / update is selected. A tab-local, account-scoped sessionStorage backup supports recovery if the book closes before saving; My Recipes offers Restore unsaved draft. It is not a cross-device backup until the server acknowledges the save. A conflicting newer draft is never overwritten by that backup.
- **Party list / Saved Recipes** references the latest public version, including your own posts. A hidden/deleted post becomes unavailable. **Party Plan** stores a snapshot and number of glasses (or servings, for food); author edits/deletions do not silently change shopping quantities. Refresh from latest explicitly replaces that snapshot. Shopping quantities merge matching ingredient names only when units agree; there are no speculative mass/volume conversions.
- **My pantry**, saved recipes and party plans belong to the logged-in account and persist across sessions, for both drinks and food. An explicit, one-time import can merge the old browser-local pantry/plan. Existing account plan quantities win; no automatic claim or overwrite of another browser user's data occurs.
- Published recipes are for sharing and reference only — they never feed into, or get fed from, the game's own Meals/Drinks ordering menu (`src/orders.ts`), which remains a completely separate, fixed system.

## Authority and persistence

All mutation routes under `/api/community/` authenticate the existing HttpOnly account cookie and reject cross-site Origin/Sec-Fetch-Site requests. No client-supplied owner is trusted. Public discovery does not disclose private drafts. Owner checks apply to edits and every item in atomic batch deletion. Recipe and library version checks return conflicts instead of overwriting another tab/device's changes. Existing account session revocation applies here too.

The existing SQLite database stores recipes, normalized photo BLOBs, library entries, reports, limits and a durable `community_audit` (actor account ID, action, target and timestamp; no recipe content, credentials or photos). It uses the existing Fly `/data` volume and therefore needs no new external storage account. Back up that database together with the rest of the application data. Recipe deletion removes it from public discovery but retains party-plan snapshots deliberately.

Photos are optional still JPEG/PNG/WebP files: 5 MB input, 16 million decoded pixels, normalized to WebP with a maximum 1600-pixel edge, auto-oriented and stripped of metadata. SVG, animated/multipage images and invalid image bytes are refused regardless of extension. Sharp processes one image at a time with cache disabled. Limit: 20 uploads/hour and 20 MB normalized image data per account. Old unreferenced uploads are reclaimed on that owner's next upload after 24 hours. Private draft photos require their owner; public images require a public recipe reference; private plan snapshots retain access for their saving account. There are no public arbitrary file paths.

Other bounds: 100 active recipes/account, 200 saved recipes, 30 drinks per party plan, 200 pantry entries, 12 publishes/hour, 10 reports/hour. Recipe text is rendered with text nodes, not HTML. Uploaders are told to use photos they own or have permission to share.

## Moderation

Set `COMMUNITY_ADMIN_ACCOUNTS` to comma-separated **account UUIDs** of designated moderators, not usernames. No account is made an administrator automatically. The authenticated `/api/community/me` response includes the current user's own account ID; administrators can also look it up in the database. This configuration is operational setup, not a credential bundled in the client.

Moderators see Review reports and can hide, restore or dismiss. Hidden posts remain in the moderation queue even after a report is dismissed, so they can still be restored. Owners may edit hidden drafts but cannot republish around the moderation decision. Hide/restore/delete/publish/draft changes are recorded in `community_audit`. No automated content classifier, comments, likes or following system is included.

**2026-11-08 (Claude), Drink/Food + the two-page detail redesign:** a forked agent drove real headless Chromium at both 1920×1080 and 390×844 against a freshly isolated local server — registration, publishing a drink and a food recipe, Discover's kind/alcohol filter interaction, the new two-page detail layout for both kinds, save/party-plan/back-link search-state restoration, edit→preview→publish→Discover, delete, full two-account data isolation, and mobile scroll/no-spurious-page-turn behavior. This is Claude's own scripted browser verification, not the user's own manual acceptance — the user has not yet personally played this round.
