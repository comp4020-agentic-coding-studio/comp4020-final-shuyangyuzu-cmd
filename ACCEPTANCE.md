# Final acceptance checklist — 2026-11-08 (updated after a second manual-review round the same day)

This records, for each area the user asked to review before acceptance, what has actually been verified and by what means — and states plainly where that verification stops short of a real human playtest. "Tests passed" and "a scripted browser agent clicked through it" are not the same thing as "a person played this and accepted it"; this document does not conflate them. Dates and round names reference the matching entries in `CLAUDE.md` and `PLAN.md`, which carry the full detail — this is the summary, not a replacement.

**This document was itself produced before the user's own manual review found three further real bugs the same day it was first written** (a tiny/off-centre house-recipe illustration, food visibly reappearing at the end of the eating animation, and inconsistent leave/away behavior across the four games) — all three are now fixed and are recorded in their own sections below. This is itself evidence for this document's own central point: agent-scripted verification, however thorough, is not a substitute for a human actually looking.

## How to read the verification column

- **Unit/HTTP suite** — `vitest run`, exercises server logic and HTTP routes directly. Proves the underlying mechanism is correct; proves nothing about what a browser actually renders or whether a human finds it usable.
- **Scripted browser (agent)** — a Playwright session driven by Claude, including real pointer/click/drag events where noted. Proves the UI actually renders and responds as coded, at the specific scenarios scripted. Still not a human's own judgement, and only as thorough as the script — three rounds in this project have each found real bugs that an earlier round's own more superficial check (e.g. HTTP-only, or a bare `.click()` instead of a real pointer event) had missed.
- **Human acceptance** — the user personally played or reviewed it and said so. This is the only category that counts as "accepted."

**Verified:** Scripted browser (agent) — the final round of the three was explicitly driven by **real UI clicks in two separate Playwright browser contexts per game** (not API calls standing in for clicks), 34/34 checks passed across all four games. Full suite 559/559 at that point, `tsc`/`check:evidence` clean.

**Not yet checked at all:** a genuine two-human playtest (two separate people, two separate real devices/networks) of any of the four games end to end — join, play a few actions, leave, rejoin.

**2026-11-08 further update — a small layout fix, the user's own direct follow-up, now deployed.** Blackjack's "Leave table" sat in the bottom controls section, separate from "Back to the bar"/"I'm away" in the header — the only one of the four games with that inconsistency, since `public/poker.js` already places both controls together in the header. **2026-11-08 update — a real bug the user's own manual review found the same day, now fixed.** Despite the 34/34-checks-passed round above, the user's own direct review found that Leave-table and Back-to-bar behaved inconsistently across the four games: clicking "Back to the bar" at Blackjack, Dominoes, or Texas Hold'em never actually set that game's own existing away flag (it just navigated), so another seated player's screen kept showing the departed player as fully present, and — because `src/position.ts`'s `effectivePosition`/`src/tables.ts`'s `getTablesStatus` only ever checked each seat's `active` flag, never `away` — the departed player's own bar avatar stayed rendered seated at the game chair forever rather than standing up and appearing at a free walkable tile, even in Vegas's own already-correct emergent "stand up on return to the bar" mechanism (which depends entirely on the seat correctly stopping being this identity's "effective position" the moment it's no longer actually occupied). Poker additionally had its own standalone bug: it had no "Back to the bar" button on an active table at all, and its `routeChanged` handler called a real, permanent `leave` (folding the hand, releasing the seat) on *every* navigation away for any reason — meaning poker could never actually support a reversible "step away" in the first place.

**Fixed:** `src/position.ts` and `src/tables.ts` now factor each game's own `away` flag into "is this identity really at the chair," closing the stand-up/display gap for all three non-Vegas games using their own existing, already-correct Vegas-style mechanism rather than new per-game code. `public/blackjack.js`/`public/domino.js`'s "Back to the bar" now calls that game's own away-toggle before navigating; `public/poker.js` gained a genuine "Back to the bar" button on the active table (previously absent) and no longer eagerly leaves on every navigation away. Invite-link/room-code UI (a stale leftover from before these three games became open-seating) was also removed from Blackjack's and Poker's table views; Dominoes never had any. Vegas's own room-code/invite/host-approval flow is completely untouched.

**Verified:** Scripted browser (agent), two separate real browser contexts, **31/32 real-click checks passed** across all four games (the one inconclusive check was independently confirmed to be the verification script's own timing issue against a reused server, re-confirmed correct via direct seat-state inspection, not a reproduced app defect) — covering: A's real "Back to the bar" click standing their avatar up at a free tile; B's own screen showing A's seat as "Away" within ~1 second with no refresh; a third identity C correctly refused A's still-reserved seat; A resuming and clicking "I'm back" clearing the Away label on B's screen within ~1s; A's real "Leave table"/"Exit game" click genuinely freeing the seat for B's screen to show as empty and for C to actually sit down; Dominoes' own "leaving ends only this pair's match" rule preserved; Blackjack/Poker's lobby-phase (pre-deal) away/resume cycle; a refresh preserving an away player's own reservation; a repeated click not double-applying; invite UI confirmed absent from Blackjack/Poker's headers; Vegas's own room code/invite/host-approval and Dominoes' manual-start-only flow both confirmed unaffected. Four new regression tests (`spec/occupancy.test.ts`) pin the `effectivePosition`/`getTablesStatus` fix down directly at the unit level. Full suite **568/568 passing**, `tsc`/`check:evidence` clean. This is Claude's own scripted two-browser verification; the user has not yet personally reviewed this specific fix round.

## 3. Eating/drinking animation and stamina

**Built:** server-authoritative stamina (decays only while actually online, +70%/+30% restore, capped at 100, zero effect on any game rule); a continuous plate/glass lift-tilt-drain cutscene; a clock-skew-robust fix so the cutscene's own end-of-window timing can't flicker or replay itself.

**Last touched:** 2026-11-07/08 (clock-skew-monotonicity fix, most recent); the animation's own geometry was last substantively rebuilt 2026-11-05.

**Verified:** Scripted browser (agent), pixel-level canvas probes, plus one documented **human rejection**.

**This is the one area with a real, recorded human-acceptance event — and it was a rejection.** The 2026-11-05 round states directly: *"The user's own real-browser manual playtest rejected the eating-animation round above outright"* — citing specific, concrete complaints (the glass reaching the eyes instead of the mouth, a floating utensil, an empty plate left hanging in the air). The round was then re-fixed and re-verified, but **only by the agent's own scripted Playwright/pixel checks afterward — there is no record of the user re-playing it and confirming the fix actually addressed what they rejected.** This is the single highest-priority item for a real human replay, precisely because it's the one place a human already found something an agent's own checks had missed and signed off as working.

**2026-11-08 update — a SECOND real human rejection, in the same manual review that found the leave/away bugs above, now fixed.** The user observed the plate visibly refilling with food right at the end of the eating animation, after it had already been emptied. Root cause: `drawEatingScene`'s "plate resting flat on the table" draw call is reached both before the first bite (correctly full) and again after the plate has fully lowered back down at the end of the window — but that one call site hardcoded a full plate regardless, ignoring `mealBeats`' own already-correct `plateConsumed` value, so the already-eaten, already-landed plate visibly became full again the instant its lift animation returned to rest. Fixed by passing `1 - plateConsumed` at that call site (the identical expression the lifted-plate branch already used) — a pure drawing-call fix, no change to the underlying `mealBeats` timing math, which was already correct. Two new regression tests (`spec/eatingAnimation.test.ts`) pin this down directly: `plateConsumed` must read a genuine 1 (never dipping back toward 0) for the entire post-landing span, and must never decrease at any point across the whole meal window. **This is now the SECOND recorded human rejection in this feature's history, and the second fix with no recorded human re-acceptance** — both the original contact-geometry rejection (2026-11-05) and this food-reappearing rejection (2026-11-08) are fixes verified only by the agent's own scripted checks since. This area's priority for a real human replay is raised accordingly.

**Known gap, stated plainly:** Two real interaction bugs were found by agent browser verification and fixed *before* this went to the user at all (a pointer-capture bug swallowing clicks on the zoom buttons; the mobile button-row-over-photo layout bug) — a genuinely good sign that the scripted verification is catching real things, but also a reminder that **zero human acceptance is recorded for the Recipe Book at any point in its history**, despite being the single feature with the highest bug-count-per-verification-pass of anything in this project. This is the second-highest-priority item for a real human replay, specifically on a real phone (not just a resized desktop browser window) for the mobile photo-drag fix, since touch-event behavior on simulated viewports doesn't always match a genuine touchscreen.

**2026-11-08 update — a THIRD real bug found by the user's own manual review (alongside the two above), now fixed.** A house recipe with no uploaded photo (e.g. Cornhusker Crush) showed its own illustration tiny and pinned to the top-left corner of the detail page's photo frame, instead of centred and reasonably sized. Root cause: `.cr-zoom-frame img,.cr-zoom-frame .cr-placeholder{...display:block}` (needed so `object-fit` works correctly on a real uploaded `<img>`, which shares this selector) had unintentionally overridden the base `.cr-placeholder{display:grid;place-items:center}` rule that centres the illustration everywhere else it's shown (cards, the editor) — inside this one new frame specifically, the illustration fell back to the browser's own default top-left block position at its own small native pixel size (the `.drink-art` box is a fixed 110×120px built for small mixology-dialog cards, never designed to scale into this far larger frame). Fixed with a dedicated centering rule scoped to exactly this frame, and sizing `.drink-art` in `cqh` (CSS container-query height, relative to the frame's own real measured height via `container-type:size`) — both axes derived from the same height unit in the illustration's own real aspect ratio, so it scales to roughly half the frame's height at any frame size without distorting. This is a pure CSS fix with no server/client logic change, so it has no unit-test equivalent; verified directly by measuring the real rendered DOM: the illustration's own bounding-box centre now lands within 0.1px of the frame's own centre, at a height of 54.6-54.8% of the frame's own height, at both 1920×1080 and 390×844 — and the existing zoom +/-/Reset buttons still scale/reset it correctly around that same centre, confirmed by reading the actual applied `transform` style before and after each click. Never touches a real uploaded photo's own saved position/zoom, and does not affect the editor's own separate photo composer or the independent left/right-page scrolling fix above.

## 5. Persistence across sessions and a server restart

**Built:** every piece of state (accounts, bar identity, stamina, held items, game rooms, recipes, images) lives in SQLite; schema changes use `addColumnIfMissing` rather than a wider `CREATE TABLE`, specifically because the latter silently does nothing to an already-existing production table; the live-sync transport has an explicit `SERVER_EPOCH` mechanism built specifically so a client survives a server process restart without getting stuck rejecting every payload as "not newer."

**Verified:** Unit suite, and this is the most rigorously covered area in the project. `spec/db-migration.test.ts` builds an **actual pre-existing-schema SQLite database by hand** for every schema change made since the project started, and asserts the new code opens it, migrates it, and preserves every existing row correctly — not just that a *fresh* database works, which would prove nothing about the real deployed volume. The epoch-restart mechanism itself was built in response to an independent review that *found and reproduced* a real bug (a restarted process's own live-sync responses being wrongly rejected as stale) before being fixed.

**Known gap:** All of this verification is against a **locally reopened SQLite file**, proving the migration and epoch logic is correct — it is not the same as an actual `flyctl machines restart` against the live production volume, which has not been recorded as tested. If "survives a restart" needs to mean "survives a real production redeploy," that specific check has not been done.

## What this document is not
