## Stack and workflow choices

I accepted Node 24, TypeScript, Hono and better-sqlite3 for a small application running on the course's single Fly machine. SQLite keeps durable state in a file on `/data`, without another database service. Hono provides the HTTP routes; TypeScript helps the agent keep server state and request shapes consistent. The plain JavaScript client and canvas avoid a framework build pipeline while allowing a custom map. The scaffold and engine are recorded in [52085e8](https://github.com/comp4020-agentic-coding-studio/comp4020-final-shuyangyuzu-cmd/commit/52085e8).

The trade-offs are explicit. SQLite and synchronous database access fit this scale but do not establish capacity for a large public service. Browser storage makes joining easy but supplies no account recovery across devices. Polling avoids connection-management complexity, while its approximately 1.5-second interval leaves the final real-time requirement unfinished. Canvas supports the spatial design but requires deliberate input and viewport checks.

I used Claude for staged implementation and another agent for the interface correction. I supplied product decisions, screenshots and objections, then asked for verification and records. `CLAUDE.md` converts those decisions into constraints: server authority, transactional writes, duplicate-action protection, private session credentials and recoverable identity. The development record is not uniformly test-first: Claude initially drove HTTP interactions before adding formal engine tests. I retain that sequence rather than describe every successful change as a red-to-green cycle.

## Crit 10 — fly by instruments

Before writing any code, I asked the agent to run a read-only setup pass: check the current branch, HEAD, tags, and working tree against origin; start the app in an isolated temporary database and run `pnpm check`/`pnpm check:evidence`; read the live Fly deployment's own status and logs without touching production data; and investigate the existing identity, authority, and logging architecture against the Crit 10 brief. That investigation found the server-side authority checks were already correct — every mutation already required a matching session, host-only actions already refused non-hosts, public responses never carried a secret — but a real gap in logging: the existing `events` table was written only to SQLite, and a live `flyctl logs` pull showed nothing but Fly's own machine-boot noise, no application activity of any kind. That baseline is recorded as its own dated entry in PLAN.md, separate from this section, because it changed nothing in the running app.

Acting on that baseline, I asked for structured, identity-correlated action logging: one line per action, success or rejection, to the server's own stdout, so a presenter at the crit can narrate entirely from `flyctl logs` rather than clicking through either browser. `src/actionLog.ts` is the new module ([31b605e](https://github.com/comp4020-agentic-coding-studio/comp4020-final-shuyangyuzu-cmd/commit/31b605e)); every existing SQLite `logEvent` call in `src/rooms.ts` gained a sibling `logAction` call at the same site in the same commit. Bar and table-binding actions that previously wrote no event anywhere — moving, sitting, standing, speaking, creating or joining a table, departing or resuming an away-from-table binding — gained their first one in [481fc5c](https://github.com/comp4020-agentic-coding-studio/comp4020-final-shuyangyuzu-cmd/commit/481fc5c), including a line that correlates a tavern character to the game player it just became at the moment a table is bound. Rejections are logged from the single place every typed error already passes through (`app.onError` in `src/server.ts`), tagged `verified: false` specifically when the rejection was a failed identity check, so a forged or stale session claim is distinguishable in the log from a legitimate action that was simply refused for another reason (wrong turn, not host, a closed room) — [aad21d2](https://github.com/comp4020-agentic-coding-studio/comp4020-final-shuyangyuzu-cmd/commit/aad21d2). A bar move is debounced to at most one logged line every few seconds per player, rather than one per tile step, since the brief's own emphasis is on telling people apart and showing what they did, not a blow-by-blow path.

I asked the agent to verify, not just implement: new direct-database tests in `spec/actionLog.test.ts` (same commit, [aad21d2](https://github.com/comp4020-agentic-coding-studio/comp4020-final-shuyangyuzu-cmd/commit/aad21d2)) confirm that two identities sharing a nickname still log distinguishably, that a wrong-secret or out-of-turn attempt never produces a success line, that a retried idempotent action logs success once rather than per attempt, and that no logged line ever contains a session secret. `ADR-access-control.md` ([87f423b](https://github.com/comp4020-agentic-coding-studio/comp4020-final-shuyangyuzu-cmd/commit/87f423b)) is the new decision record the spec itself asks for — written against the actual code, not from memory, citing the real file and line of every claim it makes about identity, authority, and now logging. 213/213 tests pass; `pnpm check:evidence` green.

[Live verification and example `flyctl logs` output recorded separately in PLAN.md's Crit 10 entries — an initial pass issuing direct HTTP requests against the live app (2026-10-16, honest about not having real separate browser profiles available), and a later pass using two genuinely isolated Playwright browser contexts against the live app (2026-10-19), each with its own cookie jar and storage. Both are stated for what they are, not inflated into the real two-person, two-machine demonstration the crit itself still requires.]

I then had my own agent review the logging work above, specifically for correctness rather than coverage, and it found two real bugs in what I'd just had recorded as done: a rolled-back outer transaction could still leave a success line in `flyctl logs` when one transaction was nested inside another (the exact shape `createTableRoom` calling `createRoom` already has in production), and a rejection's `verified` field was inferred from its error code rather than from any actual proof a session check had run — both wrong in ways a reader of the log could be misled by, not just untidy. Both were reproduced with a failing test before being touched, then fixed: `src/actionLog.ts` now patches `Database.prototype.transaction` itself once, in `src/db.ts`, so every transaction on the connection buffers its own logging correctly regardless of how deeply it's nested or which helper called it; `verified` is now backed by an explicit, per-request record of whether `requireSession`/`requireBarSession` actually passed, read back by the error handler instead of guessed from the error code. I did not treat the first version's test suite passing as proof it was correct — PLAN.md's 2026-10-17 entry records both bugs, the reproduction, and the fix in full, and ADR-access-control.md was corrected to describe the fixed design rather than quietly rewritten as if the first version had never been wrong. 217/217 tests pass after the fix.

I had the same agent review that fix a second time, specifically checking it against a shape the first round's own tests hadn't covered, and it found the fix itself still had a bug: the buffering used one flat buffer per database connection, which couldn't tell an inner transaction's own rollback apart from an outer transaction's own later, genuinely successful commit, if the outer transaction caught the inner failure and recovered. A nested transaction that failed and was recovered from still got logged as a success, alongside the real one. Reproduced directly first (two `room_created` lines logged, only one room actually in the database), then fixed by replacing the single flat buffer with a stack — one buffer per transaction level, so a level's own rollback only discards that level's own entries, and a level's own commit merges upward into whichever level is still open, never printing anything until the truly outermost commit happens. 218/218 tests pass; a live production check after deploy confirmed real traffic still logs correctly. PLAN.md's correction entry now records this as its own documented step, not folded silently into the first fix — the first fix attempt genuinely looked complete at the time, and I think it's more honest to keep that visible than to rewrite the record as if the second bug had been obvious from the start.
